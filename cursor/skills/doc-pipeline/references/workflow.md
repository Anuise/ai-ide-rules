# Doc Pipeline 工作流程參考

本文件為 `doc-pipeline` 技能的詳細運作邏輯參考，Agent 在執行過程中按需載入。

---

## 1. 輸入需求最小欄位

使用者觸發 `/doc-pipeline` 時，需提供以下資訊。若使用者的描述已涵蓋這些欄位，可直接進入產出階段。

| 欄位     | 必要性 | 說明                      | 範例                               |
| -------- | ------ | ------------------------- | ---------------------------------- |
| 專案名稱 | 必填   | 專案的正式名稱            | `TaskFlow`                         |
| 專案簡述 | 必填   | 一句話描述核心價值        | 「團隊任務管理工具，強調即時協作」 |
| 目標用戶 | 必填   | 主要使用對象              | 「10–50 人的開發團隊」             |
| 核心功能 | 必填   | 至少列出 3 個功能         | 「任務看板、即時通知、報表匯出」   |
| 技術棧   | 建議填 | 語言/框架/資料庫/部署平台 | 「Next.js + PostgreSQL + Vercel」  |
| 版本號   | 選填   | 初始版本，預設 `0.1.0`    | `1.0.0`                            |

---

## 2. 缺資訊時的提問策略

**原則：最多提問 2 個關鍵問題，避免打斷使用者的思路。**

### 提問決策樹

```
使用者輸入 →
  ├─ 有專案名稱 + 簡述 + 功能？
  │   ├─ 是 → 有技術棧資訊？
  │   │       ├─ 是 → 直接產出
  │   │       └─ 否 → 提問 Q2（技術棧）
  │   └─ 否 → 提問 Q1（核心資訊）
  └─ 資訊極度模糊 → 同時提問 Q1 + Q2
```

### 標準提問模板

**Q1（核心資訊）：**

> 請補充以下資訊，我將為你產生完整的六份技術文件：
>
> 1. 這個專案要解決什麼問題？目標用戶是誰？
> 2. 至少列出 3 個核心功能。

**Q2（技術棧）：**

> 請問預計使用的技術棧為何？包含：
>
> - 開發語言/框架
> - 資料庫
> - 部署平台（如 AWS / GCP / Vercel）
>
> 若尚未決定，我將根據需求建議適合的組合。

## 3. 產出順序與依賴關係

```
README（全局概覽）
  └─→ PRD（定義「做什麼」）
        └─→ TDD（定義「怎麼做」，引用 PRD 功能列表）
              └─→ API Doc（引用 TDD 架構中的 API 端點）
                    └─→ Operations（引用 TDD 技術棧 + API 端點）
                          └─→ Changelog（引用 PRD 功能列表作為初始 Added）
```

每份文件產出時，Agent 必須回溯前序文件，確保：

- 名詞一致（功能名、模組名、端點名）。
- 版本號一致。
- 技術選型描述不矛盾。

---

## 4. 跨文件一致性檢查清單

所有六份文件產出後，逐項核對以下清單。若發現不一致，修正後再輸出最終版本。

### 4.1 名詞對齊

| 檢查項       | 來源文件     | 對照文件                      | 驗證方式               |
| ------------ | ------------ | ----------------------------- | ---------------------- |
| 功能名稱一致 | PRD 功能列表 | TDD 模組劃分、Changelog Added | 逐條比對               |
| API 端點一致 | TDD 架構圖   | API Doc 端點列表              | Path + Method 完全匹配 |
| 專案名稱一致 | README 標題  | 所有文件標題                  | 全文搜尋               |

### 4.2 版本對齊

| 檢查項              | 來源   | 對照                   |
| ------------------- | ------ | ---------------------- |
| 版本號格式 (SemVer) | README | Changelog 最新版本區塊 |
| 版本號數值一致      | README | 所有文件 metadata 區塊 |

### 4.3 技術資訊對齊

| 檢查項     | 來源文件             | 對照文件            |
| ---------- | -------------------- | ------------------- |
| 環境依賴   | README Prerequisites | Operations 環境變數 |
| 認證方式   | TDD 安全設計         | API Doc 認證方式    |
| 資料庫類型 | TDD 技術選型         | Operations 備份策略 |

### 4.4 結構完整性

| 檢查項                            | 驗證方式                       |
| --------------------------------- | ------------------------------ |
| 每份文件通過 doc-quality-gate DoD | 逐項核對必填章節               |
| 章節間有銜接段落                  | 人工抽查 H2 → H2 切換處        |
| Metadata 區塊完整                 | 每份文件頂部有版本/日期/負責人 |

## 5. 輸出格式

### 5.1 檔案路徑

| 文件       | 輸出路徑                              |
| ---------- | ------------------------------------- |
| README     | `{{project-root}}/README.md`          |
| PRD        | `{{project-root}}/docs/PRD.md`        |
| TDD        | `{{project-root}}/docs/TDD.md`        |
| API Doc    | `{{project-root}}/docs/API.md`        |
| Operations | `{{project-root}}/docs/OPERATIONS.md` |
| Changelog  | `{{project-root}}/CHANGELOG.md`       |

### 5.2 完成摘要

產出完成後，以下列格式向使用者回報：

```
文件產出完成 ✅

| # | 文件 | 路徑 | 狀態 |
|---|------|------|------|
| 1 | README | README.md | ✅ |
| 2 | PRD | docs/PRD.md | ✅ |
| 3 | TDD | docs/TDD.md | ✅ |
| 4 | API Doc | docs/API.md | ✅ |
| 5 | Operations | docs/OPERATIONS.md | ✅ |
| 6 | Changelog | CHANGELOG.md | ✅ |

跨文件一致性檢查：通過 ✅
```
